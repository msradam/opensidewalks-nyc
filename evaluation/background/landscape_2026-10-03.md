# Comparable NYC efforts and routers to compare against, 2026-10-03

This is sections 2 and 3 of a longer research note. The other sections (TDEI status and open questions) are planning notes and are not published. Every source below was read on 2026-10-03 unless a row gives another date. "UNVERIFIED" means no primary source was reached. "Secondary" means the claim comes from another party's paper, not from the party itself. Web search was not available, so discovery ran through primary APIs instead: GitHub, PyPI, arXiv, NSF, USAspending, Socrata, CourtListener, Docker Hub, Hugging Face and the publishers' own pages. Negative findings ("nothing found") are therefore weak, and are marked as such.

Section 3 is the comparison plan as written before the run. `evaluation/compare/PROTOCOL.md` says what was run and where the plan changed.

### Notes on institutions with nothing found

NYU C2SMART, CUSP, Columbia, Cornell Tech and CUNY: arXiv API searches ("sidewalk" with "york", "pedestrian network" with "york", "wheelchair" with "route", "curb ramp", "OpenSidewalks") and GitHub repository searches ("nyc wheelchair routing", "nyc accessible routing", "opensidewalks nyc", "nyc pedestrian graph") found no sidewalk-level NYC network or router from these groups, beyond tile2net and OSCUR at NYU VIDA. GitHub hits were student projects on subway accessibility (for example `kamalbuilds/out-of-service`, MIT, pushed 2026-09-23, station routing scored on elevator data). These are weak negatives without a web search. Other arXiv papers seen are not NYC routing: OmniPath (2606.24129, LiDAR audit of the National Mall), a Seoul VLM sidewalk study (2609.17882), a NYC sidewalk-shed survey (2601.23095).

NYC DOT and MOPD: the Open Data catalogue has no pedestrian network or routing product (searches "pedestrian network", "accessible route", "wheelchair", "sidewalk", "curb ramp" on 2026-10-03). No MOPD routing tool was found.

## 3. What routing to check against

### Is there an official or published NYC router?

No sidewalk-level one. The MTA's accessible trip feature is closed and station-level. Google's wheelchair option is closed and not in its API. OpenPaths is published but routes walking legs through Google and treats ramps as points. A comparison therefore has to use an open engine run locally on the same OSM extract. The machine used had Docker and `uv` and no Java runtime, so every engine had to run in a container or from a Python wheel.

### Recommended reference and why

Primary: **ORS wheelchair, local, same extract.** It is the only engine whose hard limits cover the same physical questions as this graph's profile (kerb, incline, width, surface), so a disagreement can be traced to data or to a rule rather than to a missing concept. It is also what a reviewer is most likely to know.

Same-engine check: **Unweaver in a container** with this repo's cost function. Its job is narrower: confirm that the re-implemented search gives the same routes as the engine the profile was written for.

Baseline: **Valhalla via pyvalhalla**, pedestrian costing, `type=wheelchair`, `use_hills=0`, `max_distance` raised above 10 km. It answers "what does a good stair-avoiding foot router do on raw OSM", which is the bar a user already has.

Not recommended: GraphHopper (no wheelchair model), the ORS public API (rate limits, and its OSM snapshot differs from the pinned one). OTP only if the comparison grows to include transit legs.

### Comparison protocol

1. **Same inputs.** Build every engine from `new-york-261001.osm.pbf`. Record engine version, config and build time.
2. **Two data arms.** Arm A: each engine on raw OSM. Arm B: ORS on this graph converted back to OSM with `osm-osw-reformatter` 0.4.2 (TDEI's converter, PyPI 2026-08-24), writing this graph's ramp state as `kerb`/`kerb:height` on crossing nodes and its LiDAR incline as `incline` on edges. A difference between ORS-A and ORS-B is a data difference. A difference between ORS-B and this graph's own router is a rule or algorithm difference. Whether the converter keeps every attribute needed is UNVERIFIED and is the first thing to test.
3. **Same pairs.** Reuse the seeded 2,000 random pairs per borough behind `evaluation/reachability/reach.json`, the 8 structure landmark pairs and the 10 hand-checked routes. Snap each endpoint in each engine, record the snap distance, and report separately any pair whose snaps differ by more than 25 m.
4. **Matched settings.** This profile: 8.3% up, 10% down, kerb blocked where no surveyed ramp. ORS cannot take 8.3% (allowed values 3, 6, 10, 15), so run it at 6 and at 10 and bracket. Run ORS kerb at 0.03 and 0.06 m. Leave `minimum_width` unset in one run and at 0.9 m in another (the planimetric widths make this the one attribute this graph can test that ORS rarely sees in OSM).
5. **Measures.** (a) Route found or not, as a 2 by 2 agreement table per borough. (b) Length ratio against the same engine's plain foot route (detour). (c) Overlap: share of each route's length within 10 m of the other route. (d) Audit each engine's route with this graph's data: count steps, crossings with no surveyed ramp, and edges over the incline limits along it. Audit this graph's route with OSM tags the same way.
6. **Explaining a disagreement.** Find the first edge where the two routes part, and give it one cause: kerb data (DOT survey against OSM kerb tags or none), incline data (LiDAR against OSM `incline` or none), connectivity (gap-fill edges, snapping), structure (bridge deck and seam edges), or rule (hard limit against penalty, unknown-passes against unknown-blocks). Hand-check a stratified sample per cause over imagery, two raters, as in the v0.3.3 report.
7. **What to expect.** ORS-A will route through crossings this profile blocks, because unknown kerbs pass in ORS, and will rarely block on incline, because few NYC ways carry `incline`. That is a finding about the data, and the report should say so plainly rather than call ORS wrong.
